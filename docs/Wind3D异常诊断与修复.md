# Wind3D 异常流线诊断与修复

## 现象与结论

指定数据加载后出现两类异常：大量流线从风场区域向四周延伸到屏幕外，以及少量高风速彩色直线沿东西方向贯穿地图。检查原始文件和转换文件后确认，这不是经纬度排序颠倒造成的，而是源数据异常与线段渲染算法共同放大的结果。

原始文件为 `Wind3D.nc`，网格为 `height=1、lat=569、lon=554`，范围约为东经 `115.65937～116.31007`、北纬 `39.79544～40.30706`。转换文件中的 U/V 数组与原文件按纬度升序重排后的数组逐点一致，最大差值为 `0`，因此转换阶段没有交换 U/V，也没有破坏网格索引。

## 已确认的数据问题

### 高度缺测值被当成真实高度

原文件唯一的 `height` 是 `9.969209968386869e+36`。该数值是常见的 NetCDF 浮点缺测哨兵值，但源变量没有正确声明 `_FillValue`，旧转换器只判断数值是否为有限数，因此把它保留为真实米制高度。

单层加载器会复制出两个相邻层。对 `1e36` 量级的浮点数执行 `height + 1` 不会产生可表示的变化，最终两个高度仍相同，垂直范围退化为零。修复后，转换器会把这种未声明的单层高度哨兵值回退为 `0 m`；浏览器加载旧转换文件时也会做同样兜底并显示警告。

### 五个纬度整行是异常常量

原文件纬度索引 `41～45` 的 5 行共有 `2770` 个网格点，全部为：

```text
U = 15.0 m/s
V = 0.0020812151 m/s
```

每一行跨越全部 554 个经度点，标准差为 `0`。紧邻行的 U 平均值约为 `-0.12～-0.14 m/s`，因此这里存在约 `15 m/s` 的不连续跳变。该条带正是高风速颜色直线向东贯穿地图的来源。

由于文件没有提供可证明这些点含义的质量标记，项目不会默认删除或改写它们。转换器提供显式的 `--repair-constant-latitude-stripes` 选项，仅在开发者确认条带是坏数据后，用条带上下相邻纬度行做线性插值。

## 已确认的渲染问题

旧顶点着色器先计算一个裁剪空间方向，再把界面中的线长乘以相机相关的 `pixelSize` 后直接加到裁剪坐标。示例默认最大线长为 `400`，相机参数最高可到 `1000`，产生的扩展量与真实屏幕像素没有对应关系，短粒子步长会被放大成射向屏幕外的长线。

2026 年 10 月 14 日的第一版修复让着色器在透视除法后的屏幕坐标中计算方向，并把配置值换算为 NDC，解决了近景下把 `lineLength × pixelSize` 直接加入裁剪坐标造成的全屏爆射。但该版本仍把每条短线段强制延长到 `8～80 px` 的目标长度。相机拉远时风场地理区域在屏幕上缩小，线条却继续保持固定像素长度，因此会在全球视角形成以风场区域为中心的放射扇形。

2026 年 10 月 20 日第二版曾把 `lineLength` 改为纯“屏幕像素上限”，真实线段短于上限时完全不再延长。该方法消除了全球远景的放射扇形，但 Wind3D 单帧真实位移本来就很短，因此近景粒子也变得过小，“最大线长”控件只能截短极少数长线，视觉上近似失效。

当前实现改为按相机距离分段处理：区域近景仍按 `lineLength` 生成可读的目标像素长度，使单个粒子大小和“最大线长”控件恢复作用；三维相机高度超过约 `1500 km` 后逐渐减少人为延长，到约 `5000 km` 时完全回落到 `current → next` 的真实投影长度。过渡使用平滑曲线，避免缩放过程中突然跳变。这样修改只针对拉远后的比例失真，不再牺牲常用近景效果。示例默认目标范围为 `8～80 px`，界面“最大线长”可调范围统一为 `20～240 px`、默认 `80 px`。

“流动速度”不再使用把低速值挤在左端的线性 `0.01～5` 滑块，而是使用对数刻度映射到实际 `speedFactor=0.001～5`。默认值仍为 `0.3`，低速区间获得更多滑块行程，`0.001～0.1` 可以进行细调；核心库收到的仍是普通浮点 `speedFactor`，公开 API 没有改变。

## 当前文件的修复命令

在项目根目录运行：

```powershell
py tools\netcdf\convert_netcdf.py "C:\桌面\AAA垃圾 12.17\Wind3D.nc" `
  -o "tools\converted\Wind3D_wind3d.nc" `
  --single-level-height 0 `
  --repair-constant-latitude-stripes
```

预期日志应包含：

```text
height: 单层高度 height 是缺测哨兵值，已按 0 m 处理
repaired latitude stripe: lev index 0, lat indices 523..527
```

转换后在页面中删除旧图层并重新加载该文件。建议先保持“流动速度”为 `0.3`、“最大线长”为 `80 px`，确认流向连续后再逐步调整。

## Vercel 与公开网站边界

NetCDF 转换和异常条带修复属于开发者离线预处理，不应在 Vercel 公开页面依赖访问者本机 Python 或本地路径。需要向公开用户提供该风场时，应把修复后的文件发布到网站静态资源、对象存储或 CDN，并评估约 3.8 MB 文件的缓存、CORS 和下载成本。

浏览器端的高度兜底和屏幕像素线长修复会随静态构建部署到 Vercel，不依赖服务端、环境变量或本地常驻进程。

## 验证清单

- 确认修复后 `lev` 为 `0`，不是 `9.96921e+36`。
- 确认 U 最大值不再由连续 5 个整纬度行的 `15 m/s` 常量构成。
- 确认转换前后非异常区域的 U/V 数值保持一致。
- 执行 JavaScript 和 Python 单元测试。
- 执行 `npm run build:vercel`，确认着色器可编译并生成生产站点。
- 在浏览器桌面和移动视口检查流线不再射向屏幕外，且控制台无 WebGL 错误。
- 分别检查区域近景和全球远景：近景调整“最大线长”时粒子长度应明显变化；相机高度进入远景衰减区后，线段应逐渐随地理投影缩短，不得维持固定像素长度形成放射扇形。
- Vercel 实际预览域名仍需单独验证公开资源 URL、缓存和 CORS。
