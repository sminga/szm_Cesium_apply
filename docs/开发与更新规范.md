# 开发与更新规范

## 1. 文档目的

本规范用于统一项目后续的开发前提和更新记录方式。项目不是只供开发者本机演示的页面，而是需要通过 Vercel 部署、供其他用户在浏览器中访问和使用的网站。因此，功能是否能在开发者电脑上运行只是第一步，最终还必须考虑生产环境中的构建、资源访问、接口执行和用户体验。

## 2. 线上部署的默认前提

后续开发默认采用以下判断标准：

- 网站前端由 Vercel 构建和发布。
- 用户通过 Vercel 提供的预览域名或正式域名访问页面。
- 用户的电脑上没有本项目源码，也不一定安装 Python、Docker、Node.js 或其他开发工具。
- 用户无法访问开发者电脑上的 `D:\...` 文件、`127.0.0.1` 服务和本地转换结果。
- 浏览器只能直接访问已部署的静态资源、同源接口或允许跨域访问的外部服务。

基于这些前提，任何显示在公开网站上的操作都应具备线上可执行的实现，或者清楚说明它仅用于开发者离线准备数据。

## 3. 开发时需要检查的内容

### 3.1 前端代码

- 不写死本机绝对路径、固定盘符和本地端口。
- API 优先使用 `/api/...` 之类的同源相对地址，使预览部署和正式部署都能正常工作。
- 静态资源路径需要兼容 Vite 构建后的目录结构和 Vercel 路由。
- 对网络失败、数据格式错误、WebGL 不可用和浏览器能力不足提供可理解的界面提示。
- 避免把服务器密钥或私有配置打包到浏览器代码中。

### 3.2 服务端和数据处理

Vercel 函数通常是无状态和按请求执行的，不能假设某个进程会一直运行，也不能把需要长期保存的数据只写入函数本地目录。涉及上传、转换和大文件处理时，应先评估：

- 请求和响应的数据量是否适合函数处理。
- 执行时间是否可能超过平台限制。
- 临时文件是否会在请求结束后丢失。
- 结果是否需要保存到对象存储或其他持久化服务。
- Cesium、NetCDF、DEM 和地形瓦片是否需要单独的静态托管或数据服务。

如果某项处理更适合离线完成，可以继续使用项目内的 Python 或 Docker 工具，但处理结果应在部署前上传到线上可访问的位置。

### 3.3 配置和安全

- 公开配置和私密配置必须分开管理。
- 私密值使用 Vercel 环境变量，不进入 Git 仓库。
- 文档中的环境变量示例只能使用占位值。
- 调整环境变量时，应说明变量名、用途、适用环境和缺失时的行为，但不能记录真实密钥。

## 4. 每次更新文档的写法

每次更改完成后，在 `docs/更新日志.md` 最上方新增一节。记录详细程度应与改动风险匹配，避免重要修改记录不足，也避免纯文档修正产生大量无意义模板内容。

### 4.1 完整更新记录

以下情况使用完整更新记录：

- 页面功能、用户操作或运行时行为发生变化。
- 修改公共 API、配置格式、数据格式、依赖、构建或部署方式。
- 修改 Cesium、Shader、WebGL、GPU 粒子、地形、影像、缓存或资源生命周期。
- 修复可能影响用户数据、兼容性、安全、性能或公开 URL 的问题。
- 新增复杂功能、独立模块、本地工具或 Vercel 服务端能力。

推荐使用以下结构：

```markdown
## YYYY-MM-DD：更新标题

### 更新背景

说明原来的情况、存在的问题以及本次修改目的。

### 修改内容

按功能说明实际发生的变化，并列出关键页面、模块或接口。

### 实现说明

用容易理解的语言解释主要流程和关键技术选择。

### Vercel 部署影响

说明构建命令、输出目录、路由、环境变量、静态资源、接口或存储是否变化。

### 使用方法

给出用户可以照着完成的操作步骤。

### 兼容性与影响范围

说明旧功能、公开接口、配置、数据和浏览器兼容性是否受影响。

### 验证结果

列出实际执行过的测试、构建、浏览器验证和线上验证。没有执行的项目要明确写出。

### 错误与更正记录

记录开发过程中出现的错误、异常、失败验证或错误判断，包括产生原因、采取的更正方法、更正后的结果和仍存在的风险。如果本次没有发现需要纠正的问题，也要明确写出“本次未发现需要纠正的错误”。

### 已知限制

记录仍然存在的限制、外部依赖和后续工作。

### 相关文件

列出主要修改文件及其作用。
```

栏目确实不适用时，应简短说明原因，不需要为凑齐格式重复填写“无影响”。复杂功能、部署架构、数据流程或较多操作步骤还应创建独立专题文档，并在更新日志中提供摘要和文件名。

### 4.2 简化更新记录

纯文档、注释、错别字、链接或格式整理，并且确认不改变运行时代码、构建结果和用户操作时，可以采用简化记录：

```markdown
## YYYY-MM-DD：更新标题

### 修改原因与内容

说明为什么修改、具体改了什么，以及涉及哪些文件。

### 影响与 Vercel 说明

说明为什么不会改变运行时行为、公开网站和部署产物；如果存在影响则应改用完整记录。

### 检查结果

列出实际执行的链接、差异、格式或内容一致性检查，以及未执行运行时测试的原因。

### 错误与更正记录

记录本次发现和纠正的问题；没有时写明“本次未发现需要纠正的错误”。

### 相关文件

列出本次修改文件。
```

简化记录不是省略风险说明。如果文档变更会改变命令、配置、部署步骤、用户使用方法或公开承诺，即使没有修改代码，也应使用完整记录。

## 5. 文档质量要求

更新文档需要让没有参与修改的人也能回答以下问题：

1. 为什么要修改？
2. 修改后有什么变化？
3. 普通用户应该怎样使用？
4. 是否会影响原来的功能或数据？
5. 在 Vercel 上是否可以使用？
6. 实际做过哪些验证？
7. 还有哪些没有解决或没有验证？

如果文档不能回答这些问题，就需要继续补充，而不能只保留简短的提交式摘要。

## 6. 代码注释规范

代码注释的目标是让不了解当前实现背景的维护者能够安全地阅读、调试和继续修改代码。新增或修改代码时，至少应对关键逻辑解释以下内容：

- **目的**：这段代码解决什么问题，为什么需要存在。
- **数据**：输入来自哪里，输出是什么，单位、格式和默认值是什么。
- **流程**：异步请求、状态变化、数据转换、资源创建和释放按什么顺序发生。
- **边界**：空值、错误响应、超时、重复调用、浏览器不支持、WebGL 限制和大文件等情况如何处理。
- **环境**：哪些逻辑面向 Vercel 公开网站，哪些逻辑只面向开发者本地离线工具，以及这样区分的原因。
- **兼容性**：为什么保留某个旧字段、旧事件、旧 URL 或旧调用方式。

对于公共 API、类、复杂函数、事件处理器和配置对象，应在定义附近写清用途、参数、返回值、状态影响和调用限制。对于 GPU/Shader 参数、Cesium 图层生命周期、缓存策略、资源释放和数据格式转换等容易产生误解的实现，应重点解释“为什么这样做”，而不是只描述“做了什么”。

注释不应机械重复变量名或逐行翻译代码，也不能保留与当前实现不一致的旧说明。每次修改逻辑时，都要同步检查相关注释是否仍然准确；如果代码行为没有改变，不需要为了增加数量而添加无意义注释。

简单、自解释的内部代码可以不写注释，应先通过清晰命名、准确类型和合理拆分表达意图。JSDoc 优先用于公共 API、公共类、复杂配置和存在调用限制的函数，而不是机械覆盖每个内部辅助函数。

## 7. 文件、目录与功能说明规范

### 7.1 按职责放置代码

新增代码前应先确定其职责，再选择目录。项目当前的主要边界包括：

- `src/`：可以被其他项目复用的核心库代码。
- `example/`：部署到 Vercel 的示例工作台、页面交互、网站服务封装和公开静态资源。
- `tools/`：开发者使用的 Python、Docker、数据转换和本地服务工具，不应被误认为公开网站运行时能力。
- `tests/`：按被测业务域组织的自动测试和测试数据说明。
- `types/`：对外公开的类型声明。
- `docs/`：跨模块设计、部署、故障分析、项目结构和更新记录。

新功能应进入最接近其职责的目录。如果一个文件同时承担页面初始化、网络请求、数据转换和状态管理等多个职责，应根据实际复杂度拆分，而不是继续扩大单一入口文件。拆分的目标是让职责和依赖关系更清楚，不是为了追求文件数量。

### 7.2 功能目录 README

新增独立模块、复杂功能或工具目录时，应创建或更新对应的 `README.md`。文档应根据功能实际情况包含：

1. 功能解决的问题和适用场景。
2. 目录树或主要文件列表，以及每个文件的职责。
3. 输入数据、输出结果、关键配置和默认行为。
4. 从入口到结果的核心执行流程。
5. 安装、配置、启动和实际使用步骤。
6. 可以运行的最小代码或命令示例。
7. Vercel 公开站点能力与开发者本地工具的边界。
8. 常见错误、排查方法、浏览器或平台限制。
9. 自动测试、构建和人工验证方法。
10. 面向学习者的概念解释、关键源码入口和建议阅读顺序。

文档应让第一次接触该功能的人能够先完成使用，再理解实现。涉及专业术语时，应说明它在本项目中的实际作用，避免只列出名词或外部链接。

### 7.3 文件移动与文档同步

移动、重命名、拆分或删除文件时，需要同时搜索并更新所有引用，包括 import/export、公开入口、测试、类型声明、构建配置、静态资源路径和 Markdown 链接。项目目录结构发生变化时，应更新 `docs/项目结构.md`；增加专题文档时，应更新 `docs/README.md`；改变功能入口或操作步骤时，应更新最近一级功能 `README.md`。

完成修改前，应检查是否留下失效路径、重复实现、过时说明、无用途空目录或被构建意外收录的临时文件。清理时仍需遵守工作区保护规则，不得覆盖或删除与当前任务无关的用户修改。

## 8. GitHub 调研与技术方案选择

### 8.1 哪些修改需要调研

新增复杂功能、通用基础模块、新数据格式、新 npm 依赖，或涉及 Cesium/WebGL 核心机制时，应先进行外部技术调研。典型场景包括：

- Cesium 地形、影像、3D Tiles、Primitive、Command 或 Shader。
- NetCDF、GeoTIFF、GRIB、quantized-mesh 等标准数据格式。
- GPU 粒子、空间索引、坐标转换和复杂几何算法。
- Service Worker、Web Worker、离线缓存和浏览器文件系统能力。
- 文件上传、解析、存储、安全边界和大文件处理。
- 可能明显增加 Vercel 部署包体积、浏览器下载量或客户端内存的功能。
- 准备访问 Cesium 私有属性，或准备自行实现已有通用解决方案的功能。

修改文案、修正明确路径、补充注释、轻量 CSS 调整和现有参数的小范围修改通常不需要完整调研。是否调研应根据技术风险和重复造轮子的可能性判断，而不是按改动行数机械决定。

### 8.2 调研顺序

建议按以下顺序查找和比较方案：

1. 当前项目已有模块、依赖、测试和历史文档。
2. Cesium 官方 API Reference、Sandcastle、官方仓库、Issues 和版本变更记录。
3. Vite、Vercel、浏览器 API 或相关数据格式的官方文档和官方仓库。
4. GitHub 上成熟、活跃且许可证清楚的开源项目。
5. Stack Overflow、CSDN、稀土掘金等社区经验。
6. 在确认现有方案无法满足需求后，再设计新的自定义实现。

### 8.3 GitHub 项目评估清单

不能只以 Star 数量判断项目质量。至少应检查：

- 项目目标是否与本次需求真正一致。
- 最近提交、Release、Issue 和 Pull Request 是否仍有维护活动。
- 文档、示例、自动测试、类型声明和错误处理是否完整。
- 使用的 Cesium、Vite、Node.js 和浏览器版本是否兼容本项目。
- 是否使用 Cesium 公开 API，是否依赖容易失效的私有字段。
- 是否需要常驻后端、本地进程、数据库或 Vercel 不提供的软件。
- npm 包体积、间接依赖数量、网络请求、内存和 GPU 开销。
- 是否正确释放事件、Primitive、Texture、Tileset、Worker 和其他资源。
- 是否存在公开的安全漏洞、停止维护公告或严重未解决问题。
- 许可证是否允许当前用途、修改、公开部署和再分发。

### 8.4 许可证和采用方式

没有明确许可证的仓库不能直接复制代码、资源或数据。对于有许可证的项目，应确认是否要求保留版权、附带许可证、标注修改、公开源代码或采用相同许可证。

调研完成后，应明确采用方式：

1. 直接使用项目现有实现。
2. 使用 Cesium 或相关平台的原生公开 API。
3. 只参考开源项目的架构、算法或测试思路。
4. 新增经过审查的第三方依赖。
5. 在许可证允许且确有必要时复用少量外部代码，并保留要求的声明。

优先选择依赖更少、公开 API 更稳定、容易测试、适合 Vercel 并能明确释放资源的方案。

### 8.5 调研记录

采用第三方项目、依赖或参考实现时，应在对应功能 README 和更新日志中记录：

- 项目名称、仓库来源和调研日期。
- 使用的版本或提交状态。
- 许可证和需要履行的义务。
- 采用了哪些代码、设计或算法，没有采用哪些部分。
- 为什么不直接使用其他候选方案。
- Cesium 原生 API 是否能够满足需求；不能满足时的具体原因。
- 对 Vercel 构建、浏览器包体积、网络、内存、GPU 和安全的影响。
- 自动测试、生产构建、浏览器和线上验证结果。

网络资料只能形成候选方案。任何方案进入项目前，都必须在当前依赖版本和当前代码结构中重新验证。

### 8.6 网络不可用和调研记录边界

如果当前环境无法访问外部网络、仓库或官方文档，应明确记录“外部调研未完成”，并说明当前判断依据、风险和后续补查事项，不得凭印象编造来源、版本、维护状态或许可证结论。对于根因清楚、影响范围受控且需要及时处理的问题，可以先完成实现、定向测试和生产构建，不必因为无法完成形式化调研而停止修复。

调研记录的详细程度取决于采用程度：

- 新增依赖、复制或改写外部代码、采用重要架构或算法时，在功能 README 和更新日志中完整记录来源、版本或提交状态、许可证、采用范围和验证结果。
- 只参考思路但形成了重要设计决策时，在更新日志或专题文档中记录关键结论和选择原因。
- 仅作背景检索且最终没有采用时，可以简要记录“已评估但未采用”及主要原因，不要求在多个 README 中重复同一内容。

## 9. 按风险选择验证范围

### 9.1 文档、注释和格式

- 检查 Markdown 链接、文件名、命令和术语是否真实存在且前后一致。
- 查看目标文件差异并运行 `git diff --check`，避免空白错误或意外覆盖。
- 如果确认不影响运行时代码、配置和部署产物，可以不重复执行测试和生产构建，但要在更新日志中说明判断依据。

### 9.2 逻辑、数据和公共接口

- 修改纯函数、数据解析或转换时，先运行对应定向测试，并覆盖合法输入、边界值和失败输入。
- 修改公共 API、共享模块、配置结构或兼容分支时，除定向测试外，还应运行相关回归测试；影响范围较大时运行完整测试。
- 修改 Python、Docker 或本地服务工具时，要分别验证工具自身行为和公开网站是否仍不依赖该工具。

### 9.3 页面、Cesium 和 GPU 渲染

- 修改 UI 或用户操作时，执行与 Vercel 等价的生产构建，并在真实浏览器检查桌面、移动或关键响应式视口。
- 修改 Cesium Viewer、图层生命周期、相机、地形、影像、3D Tiles、Shader 或 GPU 粒子时，必须使用代表性数据检查实际画面、交互、控制台错误和资源释放。
- 单元测试、Shader 源码断言和构建成功只能证明部分条件，不能代替不同 GPU、DPR、浏览器和视距下的视觉验证。

### 9.4 Vercel 和线上能力

- 路由、环境变量、静态资源、Serverless Function、缓存、Service Worker 或构建配置发生变化时，至少执行 `npm run build:vercel` 或项目当前等价命令。
- 具备 Vercel Preview 条件时检查实际域名下的资源地址、接口、跨域、缓存和错误提示。
- 无法进行线上验证时，记录原因、已经完成的替代验证以及仍可能存在的风险，不能把本地结果表述为线上通过。

## 10. 性能、隐私、可访问性与依赖

### 10.1 性能和资源释放

只有在改动可能影响性能时才执行对应检查。重点包括浏览器 bundle、Cesium 静态资源、风场和地形下载量、首次加载、帧率、主线程占用、内存或显存、GPU 开销、缓存命中以及移动设备降级。切换图层、关闭功能、销毁 Viewer 或离开页面后，应确认事件监听器、Worker、Primitive、Texture、Framebuffer 和计时任务按所有权正确释放。

### 10.2 本地文件和用户隐私

- 浏览器选择的本地 NetCDF、DEM、地形或其他文件默认只在当前浏览器会话处理，不自动上传。
- 如果未来需要上传，界面和文档必须提前说明用途、大小限制、保存时间、删除方式和第三方去向。
- 控制台、错误提示、遥测和更新文档不得泄露本地绝对路径、真实 Token、用户文件内容或其他敏感数据。
- `VITE_*` 等进入前端 bundle 的变量属于浏览器可见配置，不能存放需要保密的凭据。

### 10.3 可访问性、触屏和署名

- 新增控件应具备可见焦点、合理标签和键盘操作路径，并检查触屏点击区域、文字可读性和颜色对比度。
- 持续动画、粒子和相机运动应提供暂停方式；在功能适用时尊重减少动画偏好，避免让动画成为读取关键信息的唯一方式。
- 地图、影像、地形、数据、字体、图片和第三方代码应保留许可证要求的版权、署名、Credits 和再分发声明。

### 10.4 依赖和供应链

- 新增、升级或删除 npm 依赖时同步更新 lockfile，并检查依赖许可证、维护状态、已知安全问题、间接依赖数量和浏览器 bundle 影响。
- 优先复用现有依赖和平台能力，删除已经不再使用的依赖。
- 不直接修改 `node_modules`，也不提交能够由正常安装过程重新生成的依赖产物。

## 11. 完成判断

完成标准按改动性质和风险适用，不按模板数量判断。纯文档修改不需要虚构技术调研或运行无关的 GPU 测试；运行时和公开网站修改也不能以“改动较小”为由跳过直接相关的构建、交互、兼容性或安全检查。

一项任务结束前，应确认：实现和文档一致；文件放置符合职责；关键非显然逻辑有准确注释；功能 README 和项目索引在需要时已经同步；验证覆盖本次风险；未验证部分、错误更正和剩余风险已经写入更新日志。若线上验证条件不足，至少完成与 Vercel 等价的生产构建；纯文档或注释修改不影响部署产物时，可以不重复构建，但必须说明依据。
